# danielkramer.dev — personal site

Static, single-page. Design inspired by
[marvinvonhagen.com](https://marvinvonhagen.com).

## Files

| File | Role |
| --- | --- |
| `main-site.dc.html` | **The source you edit.** Opens directly in a browser. |
| `index.html` | **What GitHub Pages serves.** Generated by `build.py` — do not hand-edit. |
| `build.py` | Rebuilds `index.html` from the source. |
| `support.js` | The runtime, used when you open the source directly. Packed into `index.html`. |
| `fonts/NeueHaasDisplayMedium.ttf` | The face used for the name in the header. Falls back to Space Grotesk if missing. |
| `worker/` | The Cloudflare Worker that hands out the contact address. Not part of the site. |

## The build step — read this first

`index.html` is not the source. It is a self-contained *bundle*: the whole
document plus the runtime, the web fonts and the typeface, packed into one file
so the live page needs nothing else. **Editing `main-site.dc.html` changes
nothing about what is served until you rebuild.** That is almost always the
reason a change "didn't show up".

```sh
python3 build.py          # rebuild index.html   ← after every edit
python3 build.py --diff   # show what would change, write nothing
python3 build.py --check  # exit 1 if index.html is stale
```

The build parses the page's script half first and **refuses to write
`index.html` if it doesn't**, pointing at the offending line in
`main-site.dc.html`. Since everything you routinely edit — the `PANELS` lists —
lives in that script, a stray comma would otherwise ship a blank page. A
missing comma between `href: '…'` and `sub: true` is the classic one.

Then commit **both** files and push.

Two ways to preview locally, and they are not the same thing:

```sh
open main-site.dc.html                 # the source — always current, no build
python3 -m http.server 8000            # then open localhost:8000 — this serves
                                       # index.html, i.e. the built page
```

If the two disagree, `index.html` is stale — run the build.

## Hosting on GitHub Pages

1. Push this folder to a repo (`<username>.github.io` for a root domain, or any
   repo name for `<username>.github.io/<repo>`).
2. Settings → Pages → Source: *Deploy from a branch*, branch `main`, folder `/`.
3. For a custom domain, add a `CNAME` file containing the bare domain.

## Editing the content

**Prose** — the paragraphs between the collapsibles — is plain text in the
template half of `main-site.dc.html`. Edit it in place.

**The lists** behind each collapsible are *not* in the markup. They live in one
place, the `PANELS` block at the top of the script half. A line is written as:

```js
'just some text',                                     // text, no link
{ before: 'text ', a: 'Label', href: 'https://…' },   // text, then a link
{ a: 'Label', href: 'https://…', after: ' — more' },  // a link, then text
{ before: 'a note', sub: true },                      // indented, dimmed
{ kind: 'mail', a: 'you@example.com' },               // click-to-copy address
{ kind: 'plate' },                                    // the plaque-assay egg
```

You never write `├─`, `└─` or the typing delays — `decorate()` derives them
from each line's position once at load, so adding, removing or reordering
lines needs no other edit. Columns are aligned with ordinary spaces; what you
type is what shows. Links starting with `http` open in a new tab; `#` is a
placeholder that stays on the page.

## Contact address

The address is **not in this repo and not in the served page**. It is a secret
on a Cloudflare Worker, handed over only after a Cloudflare Turnstile check
passes. The contact row shows `show email`; clicking it verifies the visitor
(usually with no interaction at all) and then fills the address in.

Both halves are Cloudflare, on **one account** — Turnstile is Cloudflare's own
CAPTCHA alternative, not a separate service, and it sits in the same dashboard
as Workers. Nothing else to sign up for.

This matters because the repo is public: anything in `main-site.dc.html` is
also in `index.html`, and both are on GitHub for anyone — including harvesters —
to read. Build-time injection would not have helped; only fetching it at
runtime from something that can refuse does.

### One-time setup

1. **Turnstile** — same Cloudflare dashboard you deploy the Worker from:
   Turnstile → *Add widget*. Free, and it works on a site hosted anywhere — the
   site does not have to be on Cloudflare.

   - **Hostnames**: `schulzedaniel.github.io`. Add `localhost` too if you want
     to test locally, and any custom domain you later point at the site.
     Hostnames only — no `https://`, no paths.
   - **Widget mode**: *Managed*. It pairs with the `appearance:
     'interaction-only'` the page renders with, so nothing is shown unless a
     visitor actually has to prove something.

   You get a **site key** (public, goes in the page) and a **secret key**
   (goes to the Worker, never leaves Cloudflare). Don't mix them up — the
   site key is the short one starting `0x4…`.
2. **Claim your workers.dev subdomain** — one time, per account. Dashboard →
   Workers & Pages → it prompts for a subdomain (e.g. `danielschulze` →
   `danielschulze.workers.dev`). Without this, `wrangler deploy` stops with
   *"You need to register a workers.dev subdomain before publishing"* and
   nothing goes live. Choose carefully: changing it later breaks every URL
   under it.

3. **Deploy the Worker**, from `worker/`:

   ```sh
   cd worker
   npx wrangler deploy
   npx wrangler secret put TURNSTILE_SECRET   # paste the Turnstile secret key
   npx wrangler secret put EMAIL              # paste the address itself
   ```

   First run opens a browser to authorise wrangler. That consent screen asks
   for a broad scope set because wrangler is a general-purpose CLI — this
   Worker only needs *Account → Workers Scripts → Edit*. To keep the grant
   narrow, create a custom API token with just that permission, then
   `export CLOUDFLARE_API_TOKEN=<token>` and wrangler will skip OAuth. Review
   or revoke either kind at My Profile → API Tokens.

   Check `ALLOWED_ORIGINS` in `wrangler.toml` lists every origin the site is
   served from. Requests from anywhere else — and requests with no `Origin` at
   all, which is what `curl` and scrapers send — are refused.
4. **Point the site at it.** In `main-site.dc.html`, above `MAIL_LABEL`:

   ```js
   const MAIL_ENDPOINT = 'https://email-reveal.<your-subdomain>.workers.dev';
   const TURNSTILE_KEY = '0x4AAAAAAEEeIaq6f-QhDcql';   // widget "email-reveal"
   ```

   Both are set and deployed. Leave `TURNSTILE_KEY` alone unless you
   deliberately make a new widget — changing it breaks the pairing with the
   secret on the Worker. Both are public values. After any edit here, run
   `python3 build.py` and commit.

If `MAIL_ENDPOINT` is ever blank the row reads *email available on request*
rather than breaking. Two checks that need no account and no secret:

```sh
node worker/email-worker.test.mjs      # every refusal path, siteverify stubbed
node worker/siteverify-live.test.mjs   # real call to challenges.cloudflare.com
                                       # using Cloudflare's dummy secrets
```

### Testing without going live

Cloudflare publishes dummy keys that skip the real check, so you can prove the
plumbing works before using your own. Put these in temporarily:

| Key | Value | Effect |
| --- | --- | --- |
| site key | `1x00000000000000000000AA` | always passes |
| site key | `2x00000000000000000000AB` | always blocks |
| secret key | `1x0000000000000000000000000000000AA` | always passes |
| secret key | `2x0000000000000000000000000000000AA` | always fails |

Pair the always-blocks site key with your real secret to see the failure path
(`could not verify — try again`). Swap both back to your real keys when done.

Trade-offs worth knowing:

- The address needs JavaScript and a reachable Worker, so it will not appear for
  a visitor with JS off. The other contact rows (LinkedIn, BlueSky, GitHub) are
  plain links and always work.
- Clicking `show email` pulls in a script from `challenges.cloudflare.com`. That
  is Cloudflare's own domain, not another vendor — but it is a second host, and
  it is the only thing the otherwise self-contained page ever loads. It is
  fetched on click, never on page load.

If you would rather not load that script at all, the Turnstile half can be
dropped: the Worker keeps the address as a secret and hands it over on a plain
`fetch`. That still keeps it out of the repo and out of page source — which is
what defeats harvesters, since they parse HTML and do not run JavaScript — but
there is then no actual check that the caller is human.

### Adding a collapsible section

Three pieces. No ids need registering — they are created on first use.

**1. The trigger** — a span inside any paragraph:

```html
<span role="button" tabindex="0" onClick="{{ toggle.myid }}" onKeyDown="{{ key.myid }}"
      style="cursor: pointer; border-bottom: 1px dashed var(--faint); padding: 0 1px; transition: border-color .2s ease;"
      style-hover="border-bottom-color: var(--fg);">my keyword</span>
```

**2. The panel** — right after that paragraph. Copy an existing one and change
the two ids; the row markup inside never varies.

```html
<div style="display: grid; grid-template-rows: {{ rows.myid }}; transition: grid-template-rows .42s cubic-bezier(.32,.72,0,1); margin-top: -16px;">
  <div style="overflow: hidden;">
    <sc-if value="{{ mounted.myid }}" hint-placeholder-val="{{ true }}">
      <div style="padding-top: 14px; display: grid; grid-template-columns: auto 1fr; column-gap: 10px; row-gap: 6px; font-family: 'Fragment Mono', ui-monospace, monospace; font-size: 14.5px; line-height: 1.55;">
        <sc-for list="{{ tree.myid }}" as="row">…the shared row markup…</sc-for>
      </div>
    </sc-if>
  </div>
</div>
```

**3. The lines** — a `myid:` entry in `PANELS`.

### Browser-window previews

Copy an existing block (see the iGEM or TEDx one) — the sentinel `<div ref>`, the
`<sc-if>`, and everything inside it — then change the `href`, the `<iframe src>`,
and the URL label. Two things in the logic class need a line each: the hover
handlers (`onXIn` / `onXOut` + `xArrow`), and an entry in `WIN_PANEL` naming the
collapsible panel the window sits in. Some sites block being framed; if a window
renders blank, replace the `<iframe>` with an `<img>` screenshot at the same size.

### Colours and type

All theme colours are CSS variables at the top of the file, defined twice:
`:root` (light) and `[data-theme="dark"]` (dark). Change them in both places.
Fonts are Newsreader (prose) and Fragment Mono (trees, labels), loaded from
Google Fonts in the same block.

### Preview windows load offstage

A window is never shown empty. Once its panel has finished unfolding (~1.25s) and
the sentinel has been scrolled into view, the window is built *offstage* — it is
in the page at full size, but its wrapper row is `0fr` at `opacity: 0`, so it
takes up no space and cannot be seen while the remote page loads.

While that happens, one more line types onto the end of the tree — `opening
2023.igem.wiki · · ·`, dimmed and indented under the list — so the wait reads as
something arriving rather than nothing happening. It is held back by
`HINT_AFTER` (260ms) so a cached page never flashes it. The name shown comes
from `WINDOWS[<id>].label`.

Only when the page has fired `load` does the hint collapse and the finished
frame lift open in its place, in one motion. Closing
the panel resets this, so reopening repeats the same sequence rather than
flashing a frame that is still reloading. If a site blocks framing, a 5-second
timeout shows the window anyway; swap the `<iframe>` for an `<img>` screenshot in
that case.

Each preview renders the remote page at a laptop viewport (`VIEW_W` × `VIEW_H`,
1440 × 900) and scales that down to the window's width, so the frame keeps the
site's own 16:10 proportions at any screen size instead of cropping it to a fixed
height. Change those two constants to change the shape of every window.

## Interactions

- **Dark mode** — button top right, or press `D`. Stored in `localStorage`,
  defaults to the OS setting.
- **Cursor** — the native cursor is hidden on mouse devices; a dot follows it
  and expands into a pill around anything clickable. Untouched on touch devices.
- **Plaque assay** — the last contact row shows a confluent plate; hover it and
  three plaques clear through the lawn.
- **The virion, top right** — idles as a slow shimmer, reassembles on hover, and
  plays one of five random animations on click (antibody neutralisation,
  replication, sneeze, lysis, dizzy).
- Everything degrades correctly under `prefers-reduced-motion`.
